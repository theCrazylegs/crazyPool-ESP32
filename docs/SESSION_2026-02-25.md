### 2. Bugs identifiés

#### Bug #1 — CRITIQUE : Boucle WiFi bloquante (la source des pertes de connexion)

```cpp
// Dans loop() :
if (WiFi.status() != WL_CONNECTED) {
  while ( WiFi.status() != WL_CONNECTED ) {  // BLOQUE À L'INFINI
    delay ( 500 );
    Serial.print ( "." );
  }
  // CE CODE N'EST JAMAIS ATTEINT (code mort)
  Serial.println("Connection failed.");
  delay(5000);
  return;
}
```

**Pourquoi c'est grave :** Quand le WiFi coupe (coupure réseau, redémarrage box, interférence), l'ESP32 entre dans une boucle infinie. Pendant ce temps : aucune lecture capteur, aucun affichage LCD, aucune reconnexion active. L'ESP32 est en "zombie". La boucle ne peut se résoudre que si `Wifi_disconnected()` (event handler) relance `WiFi.begin()` ET que le WiFi revient. Mais rien ne garantit que ça marche proprement.

#### Bug #2 — CRITIQUE : reconnect() MQTT bloquant

```cpp
void reconnect(){
  while (!mqttclient.connected()) {
    Serial.println("Connection au serveur MQTT ...");
    if (mqttclient.connect("ESPClient", MQTT_USERNAME, MQTT_KEY)) {
      Serial.println("MQTT connecté");
    } else {
      delay(2000);  // BLOQUE 2 secondes à chaque tentative ratée
    }
  }
}
```

**Pourquoi c'est grave :** Si le broker MQTT est injoignable (redémarrage serveur, panne réseau), la fonction `reconnect()` boucle indéfiniment avec des pauses de 2s. Rien d'autre ne tourne pendant ce temps. Cette fonction est appelée depuis la boucle principale toutes les 10s.

#### Bug #3 — Démarrage impossible sans PC

```cpp
Serial.begin(115200);
while(!Serial);  // Attend que le moniteur série soit ouvert !
```

**Pourquoi c'est grave :** En déploiement standalone (ESP32 branché sur un chargeur, sans PC), ce code attend indéfiniment l'ouverture d'un moniteur série. L'ESP32 ne démarre jamais. C'est un oubli de développement (utile pendant les tests, oublié en production).

#### Bug #4 — Boutons bloquants

```cpp
if (digitalRead(pinBtEnter)){
  ph.calibration(phVoltage,temperature,"ENTERPH");
}
while (digitalRead(pinBtEnter));  // Attend que tu lâches le bouton
```

**Pourquoi c'est grave :** Pendant que tu maintiens un bouton appuyé, toute la boucle principale est bloquée. Les capteurs ne sont pas lus, MQTT n'est pas maintenu.

#### Bug #5 — Valeurs PZEM non vérifiées

```cpp
float voltage = pzem.voltage();  // Peut renvoyer NaN si PZEM débranché
// Aucune vérification avant publication MQTT
mqttclient.publish("esp32/crazypool", (char*) jsontomqtt.c_str(), true);
```

**Pourquoi c'est grave :** Si le compteur PZEM-004T n'est pas alimenté ou déconnecté, toutes les valeurs sont `NaN` (Not a Number). Le JSON publié en MQTT contiendra `"Volt": "nan"` qui peut planter des parseurs côté Home Assistant.

#### Bug #6 — ID MQTT client hardcodé

```cpp
mqttclient.connect("ESPClient", MQTT_USERNAME, MQTT_KEY)
```

**Pourquoi c'est grave :** Si tu as 2 appareils ESP32 avec ce code, ils se déconnecteront mutuellement du broker MQTT (un broker MQTT n'accepte pas 2 clients avec le même ID — le 2ème déconnecte le 1er).

#### Bug #7 — Fragmentation mémoire (String Arduino)

```cpp
jsontomqtt = "{\"temperature\": \"" + String(temperature) +"\", \"ph\": \"" + String(phValue) + ...
```

**Pourquoi c'est grave :** L'opérateur `+` sur `String` Arduino alloue et libère de la mémoire dynamique à chaque opération. Sur un microcontrôleur avec peu de RAM, cela fragmente le heap et peut causer des crashes aléatoires après plusieurs heures/jours de fonctionnement.

#### Bug #8 — Code mort

```cpp
// mqtt_publish() → définie mais jamais appelée (utilisation directe de mqttclient.publish partout)
// print_wakeup_reason() → définie mais jamais appelée
// Code DeepSleep → entièrement commenté
```

**Impact :** Pas de bug fonctionnel mais augmente la taille du code inutilement et crée de la confusion.

### 3. Problèmes de sécurité identifiés

| Problème | Risque |
|---|---|
| Credentials WiFi dans le code source (version originale) | Exposition publique sur GitHub |
| MQTT sans chiffrement (port 1883) | Trafic interceptable sur le réseau local |
| Pas d'OTA sécurisé | Mise à jour nécessite accès physique USB |

### 4. Impact sur le WiFi personnel

Les boucles bloquantes avec `delay()` répété + `WiFi.begin()` dans l'event handler créent des **rafales de paquets de reconnexion** qui peuvent saturer le canal WiFi temporairement et provoquer des micro-coupures sur les autres appareils connectés.
